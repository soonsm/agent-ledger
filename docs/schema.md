# Agent Ledger 장부 스키마

> 상태: 확정
>
> 이 문서는 `agent-ledger.json`에서 사용하는 장부 항목의 기본 구조와 각 필드의 존재 이유를 정의한다. CLI UX와 저장 형식의 세부 구현은 별도 문서에서 다룬다.

## 1. 스키마가 표현해야 하는 것

장부 항목 하나는 단순히 "커밋할 때 물어볼 질문"이 아니다.

하나의 항목은 다음을 함께 표현해야 한다.

1. 시간이 지나도 같은 항목임을 어떻게 식별하는가?
2. 이 항목은 무엇을 의미하고 AI에게 무엇을 물어보는가?
3. 어떤 답을 유효한 값으로 인정하는가?
4. 지금도 새 커밋에서 이 항목을 사용하고 있는가?
5. 기록된 값이 얼마나 누적되면 더 큰 검토를 수행해야 하는가?

이를 각각 다음 다섯 역할로 구분한다.

```text
Identity
Meaning
Validation
Lifecycle
Feedback
```

이 구분은 개념적인 역할 구분이다. JSON에서 반드시 다섯 개의 중첩 객체로 표현한다는 뜻은 아니다. 초기 스키마는 사람이 읽고 CLI가 다루기 쉽도록 대부분의 속성을 field 객체에 평평하게 두고, 감사 관련 속성만 `audit` 객체로 묶는다.

---

## 2. 전체 구조

기본 파일명은 다음과 같다.

```text
agent-ledger.json
```

기본 구조는 다음과 같다.

```json
{
  "schema": 1,
  "fields": [
    {
      "id": "L001",
      "key": "state_flags_added",
      "description": "실행 중 값이 변하며 제어 흐름이나 동작 상태를 표현하는 상태 필드가 이번 변경에서 새로 추가된 개수",
      "question": "이번 변경에서 추가한 상태 플래그 수는? 없으면 0.",
      "type": "integer",
      "min": 0,
      "status": "active",
      "audit": {
        "aggregation": "sum",
        "threshold": 30
      }
    }
  ]
}
```

---

## 3. 최상위 필드

### `schema`

**장부 명세 파일 형식 자체의 버전이다.**

예:

```json
"schema": 1
```

이 값은 개별 장부 항목의 버전이 아니다. 향후 `agent-ledger.json`의 구조가 바뀌었을 때 CLI가 해당 파일을 해석할 수 있는지 판단하기 위해 사용한다.

예를 들어 미래 버전에서 audit 구조 자체가 호환되지 않게 바뀐다면 `schema`를 올릴 수 있다.

### `fields`

**이 프로젝트가 현재 알고 있는 장부 항목들의 목록이다.**

각 원소는 하나의 독립적인 수행 또는 판단 항목을 나타낸다.

폐기된 항목도 과거 기록 해석을 위해 `fields`에 남을 수 있다.

---

# 4. Field 역할별 정의

## 4.1 Identity — 이 항목이 무엇인지 계속 식별한다

장부는 오랜 기간 누적된다. 사람이 읽는 이름이나 설명이 바뀌더라도 과거 커밋에 기록된 값과 현재 정의가 같은 항목이라는 사실은 유지되어야 한다.

Identity는 이를 위한 역할이다.

### `id`

**절대 바뀌지 않는 내부 식별자다.**

예:

```json
"id": "L001"
```

용도:

- Git Notes에 저장된 과거 값과 현재 명세를 연결한다.
- `key`가 변경되어도 같은 장부 항목의 계보를 유지한다.
- 누적 계산과 감사 기준점을 안정적으로 연결한다.

예를 들어 처음에는 다음과 같을 수 있다.

```text
L001 → state_flags_added
```

나중에 더 적절한 용어를 찾아 다음처럼 바꿀 수 있다.

```text
L001 → mutable_state_added
```

이 둘은 이름은 다르지만 같은 `L001`이므로 같은 장부 항목으로 취급한다.

한 번 실제 장부에 사용된 ID는 다른 의미로 재사용하지 않는다.

### `key`

**사람과 AI가 읽기 쉬운 현재 이름이다.**

예:

```json
"key": "state_flags_added"
```

용도:

- CLI 출력에서 항목을 이해하기 쉽게 표시한다.
- 명세를 사람이 직접 읽을 때 의미를 빠르게 파악한다.
- 명령에서 ID와 함께 보조 식별자로 사용할 수 있다.

`key`는 용어나 설계가 발전하면 변경할 수 있다. 따라서 과거 장부와의 연결 기준으로 사용하지 않는다. 장기적인 식별 기준은 `id`다.

---

## 4.2 Meaning — 무엇을 의미하고 무엇을 판단해야 하는지 설명한다

같은 `integer` 값이라도 무엇을 세는지 알 수 없다면 장부는 의미가 없다.

Meaning은 AI가 실제로 무엇을 검토해야 하는지, 사람이 나중에 이 항목을 보았을 때 어떤 의미인지 이해하게 한다.

### `description`

**장부 항목의 개념과 판단 범위를 설명한다.**

예:

```json
"description": "실행 중 값이 변하며 제어 흐름이나 동작 상태를 표현하는 상태 필드가 이번 변경에서 새로 추가된 개수"
```

용도:

- 무엇을 이 항목에 포함하고 제외할지 판단할 근거를 제공한다.
- 시간이 지난 뒤에도 항목의 원래 의도를 이해할 수 있게 한다.
- `question`만으로 의미가 모호할 때 추가 맥락을 제공한다.

`description`은 가능한 한 특정 파일명이나 현재 수치에 의존하지 않는다. 그런 정보는 시간이 지나면 낡기 쉽다.

### `question`

**커밋 시 AI에게 실제로 답하도록 요구할 질문이다.**

예:

```json
"question": "이번 변경에서 추가한 상태 플래그 수는? 없으면 0."
```

용도:

- 필수 값이 빠졌을 때 CLI가 AI에게 무엇을 다시 검토해야 하는지 직접 알려준다.
- AI가 전체 장부 명세를 미리 기억하지 않아도 feedback을 통해 판단을 수행하게 한다.
- `0`, `false` 같은 값도 명시적으로 제출해야 한다는 사실을 질문 자체에서 분명히 할 수 있다.

`description`과 `question`의 차이는 다음과 같다.

```text
description
→ 이 항목이 정확히 무엇을 의미하는가?

question
→ 지금 이 커밋에서 AI가 무엇에 답해야 하는가?
```

## 4.3 Validation — 어떤 답을 유효한 값으로 인정할지 정의한다

Agent Ledger는 AI가 제출한 판단이 실제 코드와 일치하는지 의미적으로 검증하지 않는다.

대신 **제출된 값이 이 항목이 요구하는 형식과 제약조건을 만족하는지**는 기계적으로 검증한다.

### `type`

**항목이 허용하는 값의 종류를 정의한다.**

v1 기본 타입:

```text
integer
boolean
enum
string
```

예:

```json
"type": "integer"
```

용도:

- 잘못된 종류의 값을 거절한다.
- CLI가 AI에게 어떤 형태의 값을 제출해야 하는지 설명할 수 있게 한다.
- 누적 방식과 호환되는 값인지 판단하는 기반이 된다.

### `min` / `max`

**숫자형 값의 허용 범위를 제한한다.**

예:

```json
"min": 0
```

`state_flags_added`처럼 추가 개수를 나타내는 값에는 음수가 의미가 없으므로 `min: 0`을 사용할 수 있다.

필요한 항목에서만 사용한다.

### `values`

**`enum` 타입에서 허용하는 값의 목록이다.**

예:

```json
{
  "type": "enum",
  "values": ["passed", "failed", "not-run"]
}
```

용도:

- 자유 텍스트 때문에 같은 상태가 여러 표현으로 갈라지는 것을 막는다.
- 이후 기계적인 질의와 집계를 안정적으로 만든다.

### 제출 필수 여부

v1에서는 별도의 `required` 필드를 두지 않는다.

**`active` 상태인 모든 장부 항목은 항상 제출 필수다.** 값이 없으면 커밋을 거절한다. 반대로 `deprecated` 상태인 항목은 새 커밋에서 제출을 요구하지 않는다.

다음 둘은 명확히 구분한다.

```text
state_flags_added = 0
```

```text
state_flags_added = <missing>
```

첫 번째는 AI가 검토한 뒤 0이라고 판단했다는 assertion이다. 두 번째는 검토했는지 알 수 없으므로 유효하지 않다.

Agent Ledger는 `missing`을 자동으로 `0`, `false`, `not-run` 등으로 바꾸지 않는다.

별도의 `required` 필드를 두지 않는 이유는 v1에서 선택적 active 항목이라는 개념이 필요하지 않기 때문이다. `status`만으로 현재 관찰 대상인지 여부와 제출 의무를 동시에 표현한다.

## 4.4 Lifecycle — 이 항목을 지금도 사용하는지 관리한다

프로젝트에서 감시해야 할 문제는 고정되어 있지 않다. 새로운 항목이 생기기도 하고, 더 이상 가치가 없는 항목은 사용을 중단할 수도 있다.

그렇다고 과거 기록이 존재하는 항목을 명세에서 완전히 없애면 과거 장부를 해석하기 어려워진다.

Lifecycle은 현재 사용 여부와 과거 해석을 동시에 관리한다.

### `status`

**새 커밋에서 이 항목을 사용할지 나타낸다.**

초기 상태 값:

```text
active
deprecated
```

#### `active`

새 커밋에서 현재 사용 중인 항목이다.

새 커밋에서는 반드시 명시적 값을 제출해야 한다.

#### `deprecated`

새 커밋에서는 더 이상 값을 요구하지 않지만, 과거 장부를 해석하기 위해 정의는 유지되는 항목이다.

이미 장부에 사용된 항목을 중단할 때는 기본적으로 삭제보다 `deprecated`를 사용한다. 사용 이력이 있더라도 "이 관점을 더 이상 관찰하지 않기로 결정했다"면 정상적으로 deprecated할 수 있어야 한다.

deprecated 상태로 전환할 때는 **왜 더 이상 관찰하지 않는지 이유를 반드시 기록한다.**

필요하면 나중에 다시 `active`로 복구할 수 있다. 복구하면 새 커밋에서 다시 값을 요구하며, 현재 명세의 `deprecation_reason`은 제거한다.

### `deprecation_reason`

**항목을 더 이상 관찰하지 않기로 결정한 이유다.**

`status: "deprecated"`일 때 필수이며 비어 있을 수 없다. `active` 상태에서는 존재하지 않는다.

용도:

- 과거에 중요했던 관점을 왜 중단했는지 설명한다.
- 나중에 같은 관점을 다시 활성화해야 하는지 판단할 근거를 남긴다.
- 다른 항목으로 대체되어 폐기된 경우 그 관계를 사람이 이해할 수 있게 한다.
- 실수로 비활성화된 것인지, 의도적으로 관찰을 중단한 것인지 구분한다.

예:

```json
{
  "id": "L001",
  "status": "deprecated",
  "deprecation_reason": "상태 플래그 개수 대신 상태 전이 모델 자체를 감사하기로 했기 때문"
}
```

복구 시에는 `status`를 다시 `active`로 바꾸고 현재 명세의 `deprecation_reason`을 제거한다. 과거 Git 이력에는 deprecated와 restore가 발생했던 사실이 남는다.

## 4.5 Feedback — 언제 더 큰 검토로 전환할지 정의한다

커밋마다 남기는 값 자체가 최종 목적은 아니다.

Agent Ledger가 장부를 저장하는 이유는 **작은 변화가 얼마나 누적되었는지 기억하고, 더 넓은 코드베이스 검토가 필요한 시점을 알아내기 위해서다.**

Feedback은 해당 장부 항목이 누적 감사와 어떻게 연결되는지 정의한다.

Feedback이 필요하지 않은 단순 수행 기록은 `audit`을 가지지 않아도 된다.

### `audit`

**이 항목의 값을 누적 감사에 사용하는 방법을 정의하는 객체다.**

예:

```json
"audit": {
  "aggregation": "sum",
  "threshold": 30
}
```

### `audit.aggregation`

**마지막 관련 감사 이후 이 항목의 기록을 어떻게 누적할지 정의한다.**

예:

```json
"aggregation": "sum"
```

대표적인 방식:

- `sum`: 기록된 숫자 값을 더한다.
- `count`: 조건에 해당하는 기록 또는 커밋의 횟수를 센다.

예를 들어 `state_flags_added`는 각 커밋의 추가 개수를 더해야 하므로 `sum`이 적합하다.

### `audit.threshold`

**누적값이 어느 수준에 도달하면 해당 관점에서 더 큰 검토가 필요하다고 판단할지 정의한다.**

예:

```json
"threshold": 30
```

다음과 같은 기록이 있다면:

```text
commit A  L001 = 0
commit B  L001 = 2
commit C  L001 = 0
commit D  L001 = 1
...
```

`aggregation: sum`, `threshold: 30`인 경우 마지막 상태 모델 감사 이후 합계가 30 이상이 되면 다시 누적 감사를 수행할 시점으로 판단한다.

`threshold`는 "30이면 반드시 문제가 있다"는 의미가 아니다.

> 30만큼 관련 변화가 쌓였으므로, 이제 현재 작업 하나가 아니라 코드베이스의 누적 상태를 다시 읽어볼 가치가 있다는 뜻이다.

# 5. 역할을 한눈에 보기

| 역할 | 필드 | 답하는 질문 |
|---|---|---|
| Identity | `id`, `key` | 이 항목은 무엇이며 과거의 어느 기록과 같은 항목인가? |
| Meaning | `description`, `question` | 무엇을 의미하고 AI는 지금 무엇을 판단해야 하는가? |
| Validation | `type`, `min`, `max`, `values` | 어떤 답을 유효한 값으로 인정할 것인가? |
| Lifecycle | `status`, `deprecation_reason` | 이 항목을 지금도 새 커밋에서 사용하는가? 중단했다면 왜 중단했는가? |
| Feedback | `audit.aggregation`, `audit.threshold` | 기록이 어떻게 누적되고 언제 더 큰 검토를 시작해야 하는가? |

이 역할 구분에서 특히 중요한 것은 **Meaning과 Feedback을 분리하는 것**이다.

```text
Meaning
→ 커밋 하나에서 하는 작은 판단

Feedback
→ 여러 커밋의 작은 판단이 쌓였을 때 하는 비싼 재검토
```

Agent Ledger는 이 둘 사이를 장부로 연결한다.

# 6. 완전한 예시

```json
{
  "schema": 1,
  "fields": [
    {
      "id": "L001",
      "key": "state_flags_added",
      "description": "실행 중 값이 변하며 제어 흐름이나 동작 상태를 표현하는 상태 필드가 이번 변경에서 새로 추가된 개수",
      "question": "이번 변경에서 추가한 상태 플래그 수는? 없으면 0.",
      "type": "integer",
      "min": 0,
      "status": "active",
      "audit": {
        "aggregation": "sum",
        "threshold": 30
      }
    },
    {
      "id": "L002",
      "key": "typecheck",
      "description": "현재 변경에 대해 프로젝트의 typecheck를 수행한 결과",
      "question": "현재 변경에 대해 typecheck를 수행했는가?",
      "type": "enum",
      "values": ["passed", "failed", "not-run"],
      "status": "active"
    }
  ]
}
```

`L001`은 누적 변화의 신호이므로 `audit`을 가진다.

`L002`는 현재 커밋에서 수행 여부를 명시적으로 남기는 것이 목적이므로 반드시 누적 감사를 가질 필요는 없다.

---

# 7. 스키마 변경 원칙

- `id`는 한 번 실제 장부에 사용되면 변경하거나 재사용하지 않는다.
- v1에서 `key`, `description`, `question`은 **같은 관찰 항목의 의미를 더 명확하게 표현하는 범위에서만** 변경할 수 있다.
- `type`, `min`, `max`, `values`, `audit.aggregation`, `audit.threshold`는 기존 ID에서 변경하지 않는다.
- 무엇을 측정하거나 어떻게 판단·누적하는지가 바뀌면 기존 항목을 `deprecated`하고 새 ID의 항목을 생성한다.
- 이미 사용된 항목을 중단할 때는 기본적으로 삭제하지 않고 `deprecated`로 전환하며, `deprecation_reason`을 반드시 기록한다.
- 아직 어떤 장부 기록에도 사용되지 않은 항목만 물리 삭제할 수 있다.
- 명세 변경은 `git ledger spec ...` 명령을 정상 경로로 사용한다.
- 명세를 변경할 때는 전체 스키마 validation을 통과한 경우에만 파일을 갱신한다.

# 8. 확정된 것과 아직 남은 것

이 문서로 다음은 확정한다.

- 장부 항목을 Identity / Meaning / Validation / Lifecycle / Feedback의 다섯 역할로 본다.
- stable `id`와 사람이 읽는 `key`를 분리한다.
- `description`과 `question`을 분리한다.
- 값의 형식은 Validation에서 정의하고, 제출 의무는 Lifecycle의 `status`로 결정한다.
- 항목의 현재 사용 여부를 `status`로 관리한다. `active`는 항상 제출 필수이며 `deprecated`는 새 커밋에서 요구하지 않는다. `deprecated`에는 비어 있지 않은 `deprecation_reason`이 필수다. deprecated 항목은 `restore`를 통해 다시 active로 복구할 수 있다.
- 누적 감사가 필요한 항목은 `audit.aggregation`과 `audit.threshold`를 가진다.
- 대부분의 field 속성은 평평하게 유지하고 audit 설정만 중첩한다.
