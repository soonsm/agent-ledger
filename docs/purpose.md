# Agent Ledger의 목적

## 한 문장으로

**Agent Ledger의 목적은 AI가 현재 작업만 잘 끝내는 것을 넘어, 사람이 모든 코드를 직접 읽지 않아도 시간이 지나며 코드베이스에 누적되는 문제를 적절한 시점에 다시 검토하게 만드는 피드백 루프를 제공하는 것이다.**

Agent Ledger는 커밋 도구나 메타데이터 저장소 자체를 만드는 것이 최종 목적이 아니다. 커밋과 장부는 AI의 작업을 시간축 위에 남기고, "이 관점에서 다시 코드베이스를 볼 때가 되었는가?"를 판단하기 위한 수단이다.

---

## 문제: AI는 한 번의 작업을 잘해도 코드베이스는 나빠질 수 있다

AI Coding Agent는 이미 한 작업 안에서 수행해야 하는 많은 일을 잘 처리한다.

예를 들어 다음과 같은 작업은 명확하게 지시하고 실행 결과를 확인하기 쉽다.

- 코드를 수정한다.
- typecheck를 실행한다.
- lint를 실행한다.
- 테스트를 실행한다.
- 실패하면 다시 수정한다.

모델의 성능과 컨텍스트가 좋아질수록 이런 종류의 누락은 더 줄어들 가능성이 높다. 테스트를 추가할 때 어느 계층에 두는 것이 맞는지 검토하거나, 변경에 필요한 검증을 충분히 했는지 확인하는 것처럼 추론이 필요한 항목도 한 작업의 컨텍스트 안에서는 점점 더 잘 처리할 수 있을 것이다.

하지만 이와 다른 종류의 문제가 있다.

**각 작업은 모두 합리적이었는데, 여러 작업이 쌓인 결과 코드베이스가 나빠지는 문제다.**

예를 들면 다음과 같다.

- 버그를 하나 고칠 때마다 상태 플래그를 하나씩 추가했고, 몇 달 뒤 한 클래스에 상태 플래그가 과도하게 많아졌다.
- 필요한 기능을 추가할 때마다 한 클래스에 책임을 하나씩 더 넣었고, 어느 순간 클래스의 역할이 지나치게 커졌다.
- 당장의 문제를 해결하기 위해 예외나 허용 목록을 하나씩 추가했고, 더 이상 사용되지 않는 항목이 계속 남았다.
- 필요한 함수를 하나씩 export하다 보니 공개 표면이 계속 넓어졌다.
- 비슷한 로직을 그때그때 한 벌씩 추가했고, 시간이 지나며 여러 사본이 서로 다르게 변하기 시작했다.

이런 문제는 특정 커밋 하나를 열어서는 잘 보이지 않는다.

```text
commit A  문제 없음
commit B  문제 없음
commit C  문제 없음
...
commit N  문제 없음

합계      상태 플래그 증가
          책임 증가
          예외 증가
          공개 표면 증가
          중복 증가
```

각 변경은 그 순간의 요구사항에 비추어 정당할 수 있다. 따라서 코드 리뷰, lint, commit hook처럼 **한 번의 변경을 관찰하는 장치만으로는 원리적으로 놓칠 수 있다.**

AI가 더 많은 코드를 작성하고 사람이 개별 diff를 덜 읽게 될수록 이 문제는 더 중요해진다.

---

## 필요한 것은 더 긴 체크리스트가 아니다

이 문제를 해결하는 가장 단순한 방법은 AI에게 매번 긴 체크리스트를 주는 것이다.

예를 들어 모든 작업에서 다음을 확인하도록 지시할 수 있다.

```text
상태 플래그를 늘렸는가?
공개 표면을 늘렸는가?
예외 목록을 늘렸는가?
중복 로직을 만들었는가?
한 클래스의 책임을 늘렸는가?
...
```

하지만 이 방식에는 두 가지 문제가 있다.

첫째, **모든 관점을 모든 작업에서 깊게 검토하는 것은 비싸다.**

"이 필드는 상태인가 협력자인가?", "이 두 구현은 같은 규칙의 사본인가?", "이 클래스의 책임이 이미 너무 많아졌는가?" 같은 질문은 정규식이나 단순 lint로 정확하게 판정하기 어렵다. 코드를 읽고 맥락을 이해해야 한다. AI가 수행할 수는 있지만 시간과 토큰이 든다.

둘째, **누적 문제는 매 커밋마다 깊게 검사할 필요도 없다.**

상태 플래그가 하나 추가되었다고 곧바로 전체 상태 모델을 재설계할 필요는 없다. 문제는 하나의 추가가 아니라 여러 추가가 쌓인 결과다.

따라서 필요한 것은 모든 커밋에서 비싼 판단을 반복하는 것이 아니라 다음 구조다.

```text
작은 변화 발생
    ↓
싼 흔적을 남김
    ↓
관련 변화가 누적됨
    ↓
기준에 도달함
    ↓
AI가 해당 관점에서 코드베이스를 넓게 재검토
    ↓
검토 결과를 기록
    ↓
다시 누적 시작
```

Agent Ledger가 만들고자 하는 것은 이 피드백 루프다.

## 왜 기록이 필요한가

누적 감사를 하려면 적어도 두 가지를 알아야 한다.

1. 마지막 검토 이후 관련 변화가 얼마나 쌓였는가?
2. 마지막으로 이 관점에서 검토한 시점은 언제인가?

예를 들어 상태 플래그 감사의 기준이 `30`이라면 다음과 같이 계산할 수 있어야 한다.

```text
commit A  state_flags_added = 0
commit B  state_flags_added = 2
commit C  state_flags_added = 0
commit D  state_flags_added = 1
...

마지막 감사 이후 합계 = 30
→ 상태 플래그 누적 감사 필요
```

이 기록은 단순한 문서 메모와 다르다.

- 특정 커밋의 변경과 연결되어야 한다.
- 다음 AI 세션에서도 남아 있어야 한다.
- 기계가 합산하거나 질의할 수 있어야 한다.
- 어떤 검토가 마지막으로 수행되었는지 찾을 수 있어야 한다.
- 장부 항목의 정의가 바뀌어도 과거 기록을 해석할 수 있어야 한다.

Agent Ledger에서 `ledger`는 이 지속되는 기억을 뜻한다.

## 왜 문서를 장부로 쓰지 않는가

가장 단순한 구현은 저장소 안에 Markdown이나 JSON 문서를 하나 만들고 AI가 작업할 때마다 그 파일에 기록하게 하는 것이다.

예를 들어 다음과 같은 파일을 둘 수 있다.

```text
docs/agent-ledger.md
```

그리고 매 작업마다 AI가 여기에 값을 추가하게 할 수도 있다.

하지만 Agent Ledger는 일반 문서를 장부의 기본 저장소로 사용하지 않는다. 문서는 사람이 읽는 설명이나 정책에는 적합하지만, **AI의 다음 판단을 위한 외부 기억과 누적 카운터를 저장하는 장소로는 몇 가지 성질이 맞지 않기 때문이다.**

### 문서는 평상시 AI의 컨텍스트에 들어갈 수 있다

저장소 안의 문서는 AI가 작업을 이해하기 위해 자연스럽게 탐색하고 읽는 대상이다. `AGENTS.md`, 설계 문서, README처럼 명시적으로 참조하도록 만들 수도 있다.

장부는 성격이 다르다.

예를 들어 이전 감사에서 다음과 같이 기록했다고 하자.

```text
상태 플래그는 아직 허용 가능한 수준이다.
중복 로직은 현재 문제가 아니다.
```

다음 감사를 수행하는 AI가 이 판단을 먼저 읽으면, 현재 코드를 독립적으로 다시 판단하기보다 이전 결론에 영향을 받을 수 있다. 장부에 실물 사례, 과거 수치, 이전 AI의 해석이 계속 쌓일수록 이런 영향은 커진다.

Agent Ledger가 필요한 이유는 과거 판단을 다음 AI에게 그대로 주입하기 위해서가 아니다. 필요한 것은 주로 다음과 같은 최소한의 사실이다.

```text
마지막 감사 이후 상태 플래그가 27개 추가되었다.
마지막 상태 모델 감사는 commit abc123에서 수행되었다.
```

이 정보는 **감사를 시작할 시점을 결정할 때는 필요하지만, 평소의 코드 작성이나 감사의 실제 판단 컨텍스트에 항상 들어갈 필요는 없다.**

따라서 장부는 저장소와 함께 지속되면서도, 일반 코드와 문서를 읽는 과정에서는 자연스럽게 분리되어 있는 편이 좋다.

### 문서 기록은 누락되어도 조용히 지나갈 수 있다

AI에게 다음과 같이 지시할 수 있다.

```text
작업이 끝나면 docs/agent-ledger.md를 갱신한다.
```

하지만 AI가 이를 깜빡하면 코드와 커밋은 정상적으로 만들어지고 장부만 빠진다. 시스템은 그 차이를 알지 못한다.

```text
코드 수정
    ↓
테스트 성공
    ↓
커밋
    ↓
장부 문서 갱신을 깜빡함
    ↓
아무 오류도 발생하지 않음
```

한 번 빠진 기록은 이후의 누적값을 왜곡한다. 특히 `0`을 명시적으로 기록하는 것이 중요한 장부에서는 더 큰 문제다. 기록이 없는 것이 정말 변화가 없었다는 뜻인지, AI가 질문 자체를 검토하지 않았다는 뜻인지 구분할 수 없기 때문이다.

Agent Ledger는 이 지점을 커밋 경계에 둔다.

```text
AI가 커밋 시도
    ↓
필수 장부 항목 누락
    ↓
커밋 거절
    ↓
누락된 질문 제시
```

즉 문서에 나중에 기록하도록 부탁하는 것이 아니라, **기록이 완성되어야 커밋 경계를 통과할 수 있게 한다.**

### 문서는 커밋과의 귀속을 별도로 만들어야 한다

누적 장부에서 중요한 질문은 단순히 "현재 값이 무엇인가?"가 아니다.

```text
이 판단은 어느 변경에서 나왔는가?
마지막 감사 이후 어떤 커밋들이 이 값을 만들었는가?
특정 시점의 장부는 무엇이었는가?
```

하나의 공유 문서에 값을 계속 덧붙이는 방식도 이런 정보를 표현할 수는 있다. 하지만 그러려면 각 행마다 commit SHA, schema version, 항목 ID 등을 다시 기록하고, 문서 자체의 변경 이력과 실제 제품 변경의 관계도 관리해야 한다.

Git에는 이미 커밋이라는 시간축과 식별자가 있다. Agent Ledger는 장부 항목을 해당 커밋에 직접 귀속시키는 편을 택한다.

### 문서를 사용하지 않는 것이 목적은 아니다

문서는 여전히 중요하다.

- 어떤 문제를 왜 감시하는지 설명한다.
- 장부 항목의 의미와 정책을 사람이 이해할 수 있게 한다.
- 감사 결과를 사람이 읽을 보고서로 남길 수 있다.
- 시스템의 목적과 운영 방식을 설명한다.

다만 **정책과 설명을 담는 문서**와 **매 커밋에서 생성되는 기계적으로 질의 가능한 장부**를 같은 역할로 사용하지 않는다.

```text
문서
→ 왜 이 관점을 보는가
→ 어떻게 판단해야 하는가
→ 사람이 읽을 설명과 결과

장부
→ 어느 커밋에서 무엇을 명시적으로 보고했는가
→ 마지막 감사 이후 얼마나 누적되었는가
→ 다시 검토할 시점이 되었는가
```

둘을 분리함으로써 장부는 평상시 AI 컨텍스트를 불필요하게 오염시키지 않는 외부 기억으로 남고, 문서는 사람이 이해하고 정책을 발전시키는 공간으로 남는다.

## 왜 커밋 경계를 사용하는가

커밋은 AI 작업의 모든 의미를 완벽하게 나타내는 단위는 아니다. 그러나 현재의 소프트웨어 개발에서 다음 특성이 있다.

- 코드 변경과 자연스럽게 연결된다.
- 이미 Git이 영속적인 시간축을 제공한다.
- 변경 전후를 diff로 다시 확인할 수 있다.
- 사람이든 AI든 작업을 저장소 이력에 남기는 일반적인 경계다.
- 별도의 데이터베이스 없이 프로젝트 이력과 함께 이동할 수 있다.

따라서 Agent Ledger는 우선 **커밋을 작은 기록 단위**로 사용한다.

커밋 시 AI는 현재 장부 명세가 요구하는 모든 항목에 명시적으로 답한다.

예:

```text
typecheck = passed
lint = passed
state_flags_added = 0
duplicate_logic_added = 1
```

여기서 중요한 것은 `state_flags_added = 0`이다.

값이 없는 것과 `0`은 다르다.

- 값이 없음: AI가 이 관점을 검토했는지 알 수 없다.
- `0`: AI가 현재 변경을 검토했고 추가가 없다고 판단했다는 명시적 assertion이다.

Agent Ledger는 이 판단이 사실인지 증명하려 하지 않는다. **판단을 생략하지 않았다는 사실을 강제하는 것**이 첫 번째 목표다.

---

## 정확성을 보증하는 시스템이 아니다

Agent Ledger는 AI의 판단을 진실로 인증하는 시스템이 아니다.

AI가 실제로 상태 플래그를 두 개 추가했는데 다음과 같이 기록할 수 있다.

```text
state_flags_added = 0
```

그 값이 오판인지 거짓 보고인지 기계적으로 판별할 수 없는 경우가 있다.

이 도구는 그런 문제를 해결하려고 복잡한 정적 분석기를 만들지 않는다.

대신 다음을 보장하는 데 집중한다.

> 현재 정책에서 반드시 생각해야 한다고 정한 질문을 AI가 답하지 않은 채 커밋을 끝낼 수 없게 한다.

AI가 장부 항목을 빠뜨렸다면 커밋은 실패하고, 도구는 빠진 질문을 다시 제시한다. 실패 자체가 AI에게 돌아가는 피드백이 된다.

```text
AI가 커밋 시도
    ↓
필수 항목 누락
    ↓
Commit rejected
    ↓
"이번 변경에서 상태 플래그를 몇 개 추가했는가? 없으면 0."
    ↓
AI가 diff를 다시 검토
    ↓
명시적인 값 제출
```

완벽한 판정기를 만드는 대신 **검토 행위를 workflow 안에 넣는 것**이 목적이다.

## 왜 AGENTS.md만으로는 충분하지 않은가

AI에게 모든 규칙을 `AGENTS.md`에 적어둘 수도 있다.

하지만 그러면 규칙의 실행은 전적으로 feedforward에 의존한다.

```text
AGENTS.md
  "상태 플래그 추가 여부를 확인한다"
        ↓
AI가 기억하고 수행해야 함
```

장부 항목이 늘어나면 AI가 모든 항목을 매번 기억해야 한다. 긴 무인 작업이나 반복 작업에서는 불필요하다고 판단한 절차를 생략하거나 우회할 수도 있다.

Agent Ledger는 AI가 기억해야 할 규칙을 하나로 줄이는 것을 목표로 한다.

> 커밋할 때는 Agent Ledger를 사용한다.

현재 어떤 항목을 검토해야 하는지는 Agent Ledger가 알고 있다.

```text
AGENTS.md
  "커밋은 agent-ledger를 사용한다"
        ↓
agent-ledger commit
        ↓
현재 명세에서 빠진 항목을 기계적으로 확인
        ↓
누락된 질문을 AI에게 feedback
```

즉 **장부의 완전성은 AI의 기억이 아니라 도구의 feedback에 맡긴다.**

초기 버전에서는 AI가 의도적으로 `git commit`을 직접 실행하는 모든 우회 방법까지 보안적으로 차단하지 않는다. 별도 OS 사용자, 컨테이너, 로컬 privileged service 같은 방식은 사용자의 설정 비용이 크기 때문이다. 우선 `AGENTS.md`에서 직접 `git commit`을 금지하고, 하나의 커밋 경로 안에서는 필수 항목의 생략을 허용하지 않는 현실적인 수준에서 시작한다.

---

## 장부는 고정된 체크리스트가 아니다

어떤 누적 문제를 경계해야 하는지는 프로젝트마다 다르고, 개발하면서 새로 발견된다.

처음에는 상태 플래그만 추적할 수 있다.

```text
state_flags_added
```

나중에는 다른 문제가 중요하다는 것을 발견할 수 있다.

```text
state_flags_added
duplicate_logic_added
public_surface_added
exception_entries_added
```

반대로 더 이상 가치가 없는 항목은 폐기할 수 있어야 한다.

따라서 Agent Ledger의 장부 명세는 프로그램 코드에 고정하지 않는다. 프로젝트가 자신의 장부 명세를 가지며, 명세 자체도 추가·수정·폐기할 수 있는 데이터로 취급한다.

이 설계는 중요한 전제를 반영한다.

> 코드베이스에서 무엇을 경계해야 하는지에 대한 지식도 개발 과정에서 진화한다.

---

## 피드백 주기는 항목마다 달라질 수 있다

모든 누적 문제를 `30 commits` 같은 하나의 기준으로 검사할 필요는 없다.

각 검토는 자신과 관련된 신호를 가질 수 있다.

예:

```text
상태 모델 감사
→ state_flags_added의 누적 합

테스트 구조 감사
→ 테스트 관련 변경의 누적 횟수

공개 API 감사
→ public_surface_added의 누적 합

IPC 경계 감사
→ IPC 관련 변경의 누적 횟수
```

결국 Agent Ledger가 제공해야 할 핵심 정보는 단순히 "커밋이 몇 개 있었는가"가 아니다.

> **마지막 검토 이후, 이 검토와 관련된 변화가 얼마나 누적되었는가?**

이 값이 기준에 도달하면 AI가 다시 넓은 문맥에서 코드베이스를 읽는다.

---

## 사람의 역할이 사라지는 것이 목표는 아니다

Agent Ledger의 목적은 AI가 모든 품질 판단을 대신하게 하는 것이 아니다.

사람이 모든 diff를 직접 읽지 않는 개발 방식에서도 다음이 가능하도록 만드는 것이 목표다.

- 어떤 관점을 계속 감시할지 사람이 정의한다.
- AI는 각 변경에서 필요한 최소한의 assertion을 남긴다.
- 시스템은 관련 변화의 누적을 기억한다.
- 기준에 도달하면 AI가 더 넓은 범위의 검토를 수행한다.
- 결과를 사람이 확인하거나 다음 정책을 결정할 수 있다.

즉 사람의 역할은 모든 코드 줄을 계속 감시하는 것에서, **어떤 피드백 루프가 필요한지 설계하고 그 결과를 관리하는 것**으로 이동할 수 있다.

---

## Agent Ledger가 성공했다는 것은

Agent Ledger가 성공했다는 것은 많은 메타데이터를 저장했다는 뜻이 아니다.

다음과 같은 개발 흐름이 자연스럽게 유지되는 것이 성공이다.

```text
AI가 작은 작업을 반복한다
        ↓
각 작업에서 필요한 최소한의 판단 흔적이 남는다
        ↓
사람이 기억하지 않아도 관련 변화가 누적된다
        ↓
검토할 만큼 쌓였을 때 시스템이 알려준다
        ↓
AI가 현재 작업이 아니라 코드베이스의 누적 상태를 다시 읽는다
        ↓
필요하면 구조를 정리하거나 새로운 감시 항목을 추가한다
```

최종적으로 원하는 것은 장부가 아니다.

**AI가 작성하는 코드의 양이 늘어나고 사람이 개별 변경을 덜 보게 되어도, 코드베이스가 장기간에 걸쳐 잘못된 방향으로 조용히 누적되는 것을 방치하지 않는 개발 시스템**이다.

Agent Ledger는 그 시스템에 필요한 지속적인 기억과 피드백 트리거를 제공하기 위한 하나의 수단이다.
